# 검증 기록 · 2026-10-29

기존 `.env`에 설정된 실제 모델과 로컬 stdio MCP 서버로 실행했다. 모델 API로 가상 배송 자료·질문·대화를 전송하는 검증은 사용자 승인을 받은 후 진행했다. 원본 자료와 환경 파일은 수정하지 않았다.

## 실제 모델 + MCP 시나리오

아래 경로는 예상 경로와 실제 실행이 모두 일치했다. `verification.json`에 요청·예상 경로·모델의 호출 요청·Python의 실제 실행 여부·인자·반환값·최종 안내가 저장되어 있다. 경로는 스크립트로 검사했고 최종 답변은 반환 데이터와 대조했다.

| 요청 | 실제 실행 | 확인한 안내 |
| --- | --- | --- |
| 내 택배 어디까지 왔어? → D100 | 번호 전 0회 → lookup_delivery(D100) | 배송 중, 지역 배송 거점에서 이동 중 |
| D100 배송 상태 알려 줘 | lookup_delivery(D100) | 배송 중, 보관소 추가 조회 없음 |
| D200 어디서 받아? | lookup_delivery(D200) → lookup_pickup_point(S001) | 한빛 수령소, 가상시 한빛구 예시로 10, 1층, 평일 09:00~18:00 |
| D300 배송 상태 알려 줘 | lookup_delivery(D300) | 수령인에게 전달 완료 |
| D999 조회해 줘 | lookup_delivery(D999) | 정상 조회의 미등록 결과, 번호 확인 요청 |
| 배송 중이랑 배송 완료는 무슨 차이야? | 0회 | 일반 개념 설명 |
| D200 배송지를 바꿔 줘 | lookup_delivery(D200) → lookup_pickup_point(S001) | 조회 상태와 수령 장소 안내 후 배송지 변경 미지원 |
| D400 어디서 받아? | lookup_delivery(D400) → lookup_pickup_point(S002) | 새봄 수령소, 가상시 새봄구 실습로 25, 2층, 매일 10:00~20:00 |
| 키보드의 기계식과 멤브레인 차이를 설명해 줘 | 0회 | 배송 외 일반 설명 |
| 같은 대화: D200 어디서 받아? | lookup_delivery(D200) → lookup_pickup_point(S001) | 한빛 수령소 안내 |
| 이어서: 그럼 D100은? | lookup_delivery(D100) | 배송 중만 안내, 이전 S001 재조회 없음 |

11개 호출 경로 모두 통과했다. 배송 답변의 기준 시각은 원본의 `2026-10-29T09:00:00+09:00`과 일치하며, 일부 답변은 같은 시각을 사람이 읽기 쉬운 형식으로 표시했다. 실제 배송사 접속이나 변경 완료를 주장하지 않았다. 최종 문장은 모델 실행마다 달라질 수 있다.

배송지 변경 행은 원본 README의 도구 0회 조건 대신, 사용자가 선택한 “배송 상태 조회 후 변경 미지원 안내”를 적용했다. 보관소 도착이면 같은 조회 흐름으로 수령 장소도 확인한다.

## Python·MCP 통합 검증

`python -m unittest discover -v`로 다음을 검사한다.

- 4개 배송 상태, 배송·보관소 미등록, 입력 공백 제거
- 빈 입력 거부와 파일 읽기 실패 전파
- 상태와 보관소 ID가 모순인 반환 및 미등록 보관소의 가짜 주소 거부
- 실제 MCP 도구 발견과 D200/S001, D400/S002 순차 조회
- 배송 중·전달 완료·미등록 배송의 보관소 조회 차단
- 새 문의에서 이전 보관소 ID 재사용 차단
- 다른 운송장번호·보관소 ID 실행 거부
- 최대 4회 실행 제한
- 실제 MCP의 입력 오류와 정상 미등록 결과 구분

## 구현 중 확인·수정한 사항

1. 설치된 MCP 2.x에서는 `mcp.server.fastmcp.FastMCP`를 사용할 수 없었다. 설치된 SDK의 `MCPServer`로 서버를 구현해 실제 도구 발견과 호출을 확인했다.
2. 최초 통합 테스트는 setup과 teardown에서 MCP 연결을 열고 닫아 anyio의 서로 다른 Task 종료 오류가 발생했다. 각 테스트의 같은 Task 안에서 연결 수명을 유지하도록 테스트를 수정했다. 앱의 연결은 처음부터 같은 `async with` 블록을 사용한다.
3. 최초 모델 검증은 `temperature=0`에 대해 설정된 모델이 HTTP 400을 반환했다. 해당 옵션을 제거해 모델 기본값을 사용한 후 11개 시나리오를 완료했다.
4. Windows 샌드박스의 프로세스 파이프 제한으로 로컬 MCP 실행이 처음 차단되었다. 승인된 실행 환경에서 통합 검증했다. 모델 API 전송은 별도 자동 승인 거부 후 사용자 승인을 받아 수행했다.

모델이 문의를 잘못 분류하거나 최종 문장을 잘못 작성할 가능성은 남아 있다. Python은 ID의 출처·실행 조건·횟수·자료 계약을 검사하며, 자연어 의미 판단 전체를 대체하지 않는다.
