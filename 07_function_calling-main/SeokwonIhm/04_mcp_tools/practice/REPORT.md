# 카페 MCP 도구 연결 실습 보고서

- 실습 선택: A. 내가 만든 도구를 MCP로 제공하기
- 주제: 기존 카페 메뉴 조회 함수를 MCP 도구로 사용하여 자연어 문의에 답하기
- 작성일: 2026-10-28
- 기록 근거: 현재 소스 코드, 실습 중 실제 실행 출력, 학습자가 대화에 공유한 출력과 확인 내용

## 1. 목표와 구현 범위

사용자가 입력한 예산·종류·온도로 실제 메뉴를 조회하고, 재고가 있는 메뉴만 추천하는 프로그램을 구성했다. 기존 카페 서버를 재사용하고, 도구 발견·직접 호출·모델 연결을 단계별 클라이언트로 작성했다.

서버는 가격·종류·온도로 메뉴를 필터링한다. 품절 메뉴도 조회 결과에는 포함되며, 최종 추천 시 재고가 있는 항목만 사용하도록 모델에 지시한다. 조건에 맞는 메뉴가 없으면 조건을 임의로 바꾸지 않고 없다고 답하도록 한다.

최종 프로그램은 `input()`으로 문의 한 개를 받아 응답 후 종료한다. 예산을 질문한 뒤 후속 입력을 받는 다중 턴 대화는 구현하지 않았다.

## 3. 서버 연결 방식

로컬 `01_menu_server.py`에 stdio 방식으로 연결한다. 클라이언트가 현재 가상환경의 Python으로 서버 프로세스를 시작하므로 서버를 먼저 별도로 실행할 필요는 없다.

```python
parameters = StdioServerParameters(
    command=sys.executable, args=[str(SERVER_PATH)]
)
async with stdio_client(parameters) as (read, write):
    async with ClientSession(read, write) as session:
        await session.initialize()
```

`initialize()`로 통신 준비를 마친 뒤 `list_tools()`로 도구 정보를 받는다.

## 4. 발견한 도구의 사용법

실제 도구 목록 조회에서 `lookup_menu`와 `lookup_menu_text`를 확인했다. 모델에는 이번 실습의 대상인 `lookup_menu`만 제공했다.

- 이름: `lookup_menu`
- 설명: “최대 예산 이하 메뉴를 조회한다. 종류·온도는 생략하면 전체다. 재고 0은 품절이다.”

| 인자 | 타입과 허용 범위 | 필수 여부 |
| --- | --- | --- |
| `max_price` | 정수, 0 이상 | 필수 |
| `category` | 전체, 커피, 차, 에이드 | 선택, 기본값 전체 |
| `temperature` | 전체, HOT, ICE | 선택, 기본값 전체 |

도구 목록의 입력 스키마에서 `required: ["max_price"]`와 `max_price`의 `minimum: 0`을 확인했다. 서버는 CSV의 숫자를 정수로 변환하고 Pydantic 모델로 메뉴 행을 검사한다.

## 5. 모델과 MCP 실행의 연결

```text
사용자 입력
  → list_tools로 받은 도구 사용법을 bind_tools로 모델에 제공
  → 첫 ainvoke: 모델이 도구 이름·인자·호출 ID 반환
  → 클라이언트가 call_tool로 서버에 실행 요청
  → 서버가 실제 메뉴 결과 반환
  → 같은 호출 ID의 ToolMessage로 결과를 대화 기록에 추가
  → 다음 ainvoke: 모델이 결과를 근거로 최종 답변 작성
```

`bind_tools()`는 도구 사용법을 모델에 제공하며, 도구를 실제로 실행하지 않는다. 실제 실행 요청은 다음 코드가 담당한다.

```python
result = await session.call_tool(call["name"], call["args"])
```

결과는 모델이 요청할 때 발급한 ID와 연결한다.

```python
messages.append(ToolMessage(
    content=result.model_dump_json(),
    tool_call_id=call["id"],
))
```

`messages.append()`는 기록에 추가하는 동작이다. 그 뒤 `model.ainvoke(messages)`를 호출해야 모델이 조회 결과를 읽고 최종 답변을 만든다. 도구 요청이 없으면 첫 모델 응답을 최종 안내로 사용한다.

## 6. 실제 실행 기록

### 6.1 도구 목록 조회 — 실행 출력 확인

`01_discover_tools.py` 실행에서 “서버 연결 성공!”과 두 도구의 이름·설명·입력 스키마가 출력되었다. 이 단계는 연결과 도구 발견을 확인한 것으로, 메뉴 조회나 모델 호출은 수행하지 않는다.

### 6.2 5천 원 이하 아이스 커피 직접 호출 — 실행 출력 확인

`02_call_menu.py`에 아래 인자를 넣고 실행했다. 이 단계의 인자는 모델이 아니라 코드에서 지정했다.

```json
{"max_price": 5000, "category": "커피", "temperature": "ICE"}
```

실제 반환 데이터에서 확인한 항목을 발췌하면 다음과 같다.

| 메뉴 ID | 이름 | 온도 | 가격 | 재고 |
| --- | --- | --- | ---: | ---: |
| M002 | 아메리카노 | ICE | 4000 | 12 |
| M004 | 카페라떼 | ICE | 5000 | 0 |

`is_error`는 `false`였다. 조회 조건에는 재고 필터가 없으므로 품절 카페라떼도 포함되었다. 모델을 호출하지 않았으므로 이 실행에는 최종 자연어 답변이 없다.

### 6.3 3천 원 이하 아이스 커피 직접 호출 — 실행 출력 확인

호출 인자를 다음과 같이 변경하고 실행했다.

```json
{"max_price": 3000, "category": "커피", "temperature": "ICE"}
```

실제 MCP 응답의 관련 필드 발췌:

```json
{
  "structured_content": {"menus": []},
  "is_error": false,
  "result_type": "complete"
}
```

조회는 성공했으나 조건을 만족하는 메뉴가 없었다. 빈 결과는 실행 실패가 아니다. 보고서 작성 시점의 `02_call_menu.py`에도 최대 예산이 3000원으로 저장되어 있다.

### 6.4 3천 원 이하 아이스 커피 모델 연결 — 학습자가 공유한 실행 로그

테스트 조건은 3천 원 이하·커피·ICE였다. 실제 입력 문장 원문은 공유되지 않았으므로 재구성하여 기록하지 않았다.

모델의 도구 요청 원문:

```text
[{'name': 'lookup_menu', 'args': {'max_price': 3000, 'category': '커피', 'temperature': 'ICE'}, 'id': 'call_XE074wzzMqW9BLyp2KWl22fP', 'type': 'tool_call'}]
```

실제 MCP 응답의 관련 필드 발췌:

```json
{
  "structured_content": {"menus": []},
  "is_error": false,
  "result_type": "complete"
}
```

최종 안내 원문:

```text
3000원 이하의 아이스 커피 메뉴가 없습니다.
```

모델이 올바른 조건을 선택했고, 빈 결과에 근거해 메뉴가 없다고 답했다. 현재 코드에서는 위 요청 ID를 그대로 `ToolMessage.tool_call_id`에 전달한다. 실제 `ToolMessage` 객체 자체를 출력한 로그는 없으므로 ID 전달에 대한 근거는 소스 코드와 개발 중 수행한 모의 응답 검증이다.

### 6.5 5천 원 이하 아이스 커피 모델 연결 — 학습자 확인, 전체 로그 없음

제시한 테스트 요청은 “5천 원 이하의 아이스 커피를 추천하고 가격과 재고를 알려 줘.”였다. 예상 동작은 아메리카노 4000원·재고 12개를 추천하고, 재고 0개의 카페라떼는 추천에서 제외하는 것이었다.

학습자는 “응 정확히 답이 나와.”라고 확인했다. 다만 실제 입력·호출 인자·서버 응답·최종 답변의 전체 로그는 공유되지 않았다. 따라서 사용자 확인 사례로 기록하며, 최종 답변 문장을 실제 로그처럼 만들어 넣지 않는다.

### 6.6 예산 없는 요청 — 최종 답변 원문 확인

제시한 테스트 요청은 “아이스 커피 추천해 줘.”였다. 학습자가 공유한 최종 출력은 다음과 같다.

```text
최종 안내: 예산이 얼마인가요? (원)
```

예산을 묻는 답변은 확인했다. 이 실행의 `tool_calls` 로그는 공유되지 않았으므로 도구를 호출하지 않았는지는 로그만으로 확정하지 않는다.

이후 PowerShell에 입력한 `4000원`이 명령어 오류를 낸 것은 프로그램 종료 후 셸에 입력했기 때문이다. README 요구에 맞춰 새로운 문의는 프로그램을 다시 실행하여 입력한다.

## 7. 예상 결과와 미확인 항목

| 항목 | 예상 결과 | 확인 상태 |
| --- | --- | --- |
| 음수 예산 `max_price=-1000` 직접 호출 | 0 이상 조건 위반으로 도구 오류 | 학습자가 다음 단계로 진행했으나 실제 응답과 오류 로그는 공유되지 않음. 실행 결과 확정 보류 |
| 예산 없는 문의에서 도구 미호출 | `tool_calls`가 빈 목록이고 예산 질문 | 예산 질문 출력만 확인. 도구 미호출 로그 미확인 |
| 모든 질문에서 조건 준수 | 임의 조건 변경이나 근거 없는 추천 없음 | 확인한 사례에 한정하여 평가. 모든 입력에 대한 보장은 아님 |

음수 예산 검사는 빈 결과와 잘못된 요청을 구분하기 위한 추가 테스트이다. 현재 파일은 3000원으로 저장되어 있으며, 음수 입력 테스트가 실제 수행되었다는 파일 근거나 로그는 없다.

## 8. 결론과 학습 내용

도구 발견, 직접 호출, 모델의 호출 요청, 실제 조회 결과의 전달과 최종 답변을 단계별로 연결했다. 전체 로그가 공유된 3천 원 사례에서는 요청 조건·서버의 빈 결과·최종 안내가 일치했다. 5천 원 품절 제외 사례는 학습자 확인을 받았으며, 예산 누락 사례는 예산 질문 원문을 확인했다.

서버의 입력·반환 검증과 모델에게 주는 답변 지시는 서로 다른 역할이다. 서버는 실제 조회와 데이터 검사를 담당하고, 모델은 결과를 읽어 사용자에게 설명한다. 현재 프로그램은 추천 규칙을 프롬프트로 지시하며 최종 자연어 답변의 조건 준수를 별도 코드로 강제하지 않는다. 따라서 성공한 사례를 전체 입력에 대한 정확성 보장으로 해석하지 않고, 새로운 조건에서는 호출 인자와 실제 결과를 다시 대조해야 한다.
