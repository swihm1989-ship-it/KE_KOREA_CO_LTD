# KE KOREA Master · 근거 확인형 Contract RAG 2.0 (2026-11-13)

## 목표
단순 키워드/벡터 유사도를 넘어 **원본 SHA 검증 → 조항 분할 및 부모 문맥 → 계약 유형별 검색 → 다른 원본과 교차 비교 → 거래조건 우선 초안 → 전체 계약 재감사** 절차로 연결한다.

## 저장소 구조
기존 Supabase 비공개 버킷 \`kekorea-contracts\`와 \`public.kekorea_contract_references\`의 \`source_locations\` JSONB를 그대로 사용한다. 새 SQL 스키마 변경은 없다.
- \`source_locations[0].manifest.chunks\`: 승인된 익명화 메모. 실제 원문 위치에 연결되었을 때만 \`source_section_id\`가 생긴다. 새로운 필드는 선택적이며 이전 데이터 호환을 유지한다.
- \`source_locations[kind=private_clause_hierarchy_v1]\`: 관리자용으로만 사용되는 원본 SHA256·조항 위치·원문·미추출 페이지 정보. 승인되지 않으면 AI 요청/embedding 전송에 절대 포함하지 않는다.
- \`extracted_text\`: 관리자/서버용 비공개 원문 텍스트. 일반 RAG 검색은 \`manifest.chunks[].text\`만 사용한다.
- 관리자가 검토한 원문 조항의 익명화 요약은 기존 manifest 청크에 **추가**되고 모델과 512차원 임베딩에도 해당 승인 청크만 전달된다. 미승인 조항과 개인·계좌 정보는 전송 금지.

## 관리자 활성화
1. 기존 계약서 관리 → **공통 샘플 라이브러리 관리** → 별도 관리 키 인증.
2. **원본 계약서 조항 인덱스 · 관리자 검증**에서 최대 5개 원본을 SHA256 검증 후 조항별로 비공개 추출. 한 번에 5개씩 반복. 이미지 스캔 PDF·지원되지 않는 XLSX는 억지로 색인하지 않는다.
3. 검토할 원본 선택 → **원본 조항 문맥 확인 및 개별 승인** → 조항 선택. 앞뒤 원문은 관리자만 열람.
4. 자동 마스킹 초안에서 남아 있는 실명·법인명·주소·계좌·상품별 금액·수수료율·기한·고유 거래조건을 직접 제거, 조항 주제와 내용을 검토하고 승인. 관리자가 확인한 문구만 새 RAG 청크로 등록한다.
5. **승인 참고 조항의 누락 임베딩 생성**으로 512차원 벡터 보완. 모델 설정/계정 키 문제 발생 시 키워드 검색으로 계속 동작한다.
6. 새로운 계약서 초안 생성 시: 현재 거래조건 분석 → 주제별 승인 검색 → 원문 근거가 있는 2개 이상의 서로 다른 계약서에서 유사 조항 발견 시 1회의 bounded AI 교차 비교 → 선택 근거 및 인접 **승인된** 조항 문맥 반영 → 초안 → 기존의 전체 계약 조항 감사 및 1회 국소 보완.
7. 완성된 계약의 **이번 계약에 참고한 공통 샘플**에서 선택 이유/비교 주제/검토 충돌을 확인한다.

## 검증 규칙 및 실패시 동작
- 원본 파일 SHA256이 DB 원본 해시와 다르면 저장 중단. 동일 파일 재인덱스는 idempotent.
- 조항별 공개 전 **관리자의 명시적 승인**이 필수. 이메일/전화/계좌/금액/비율 정규식도 2차 차단하지만 자동 마스킹은 완전한 개인정보 제거를 보장하지 않으므로 인적 검토가 반드시 필요하다.
- 비교는 **서로 다른 원본 문서**의 리뷰 완료 청크 2개 이상인 주제에서만 발생. 범용 메모(기존 일반화된 108개 등)는 출처 조항 증명 없이 교차 비교 후보로 신뢰하지 않는다.
- AI의 선택 ID가 제공된 근거에 없으면 무시. AI 비교 실패 시 원본 승인 메모에 근거한 검색으로 복귀하며 임의 승인하지 않는다.
- 현재 계약의 명시적으로 확인된 상거래 조건이 모든 과거 사례보다 우선. 과거 수수료율, 지급일, 법인명, 계좌번호, 보증, 준거법 등을 그대로 승계하지 않는다.
- 인접 문맥은 **이미 승인한** 조항에서만 구성. 승인하지 않은 원문은 비공개 저장소에만 존재한다.
- 최종 계약 감사는 선택 근거와 확정 조건이 충돌하지 않는지 검토한다. 이는 법적 타당성 보증이나 변호사의 검토를 대체하지 않는다.
- 계약 초안/최종 승인, 문장 메모·revision, 기존 서식(PDF, PI/PO/CI/PL)은 그대로 유지한다.

## 남은 운영 데이터 작업
2026-11-13 기준 기존 공통 승인 23개·143개 검색 청크 중 35개만 벡터가 있었고, 최근 등록 문서 20개의 \`extracted_text\`가 비어 있었다. 이 변경은 **인덱스 생성 및 관리자가 승인하는 도구 제공**이며 실제 20개 원문 추출·승인이나 108개 임베딩이 완료되었다는 뜻이 아니다. 운영 서버 키로 앱에 접속해 관리자 인덱스를 실행하고, 원문 품질/비식별화/검색 품질을 검증해야 한다.

### 2026-11-13 · ZIP 기존 OCR/텍스트 저장 누락 복구
- 관리자 인증 후 **공통 샘플 라이브러리 관리 → 기존 ZIP에서 추출했던 원문 텍스트 복구**: 기존 `contracts.zip`에서 복원한 비공개 JSON 20개를 읽는다. 저장 전에 레코드 내용 해시와 Supabase Storage 원본 바이트 SHA-256을 모두 검증한다.
- `restore_private_extraction_bundle()`는 비어 있는 `extracted_text`만 채운다. 기존 승인 청크·기존 본문·계약 revision·원본 버킷은 보존하며 `private_text_extraction_v1` 출처/미추출 페이지/검토 필요 정보를 남긴다.
- 그 다음 **원본 계약서 조항 인덱스 · 관리자 검증**을 실행하면, 기존 추출 텍스트의 페이지/문서 위치를 재사용해 비공개 계층형 조항 인덱스를 생성한다. 기존 PDF를 무조건 새로 OCR하지 않는다.
- OCR 글자 인식 오류, 스캔 미추출 페이지, 편집 누락, 서식 깨짐은 자동으로 법적 검증되지 않는다. 원문 확인과 **원문 조항 개별 승인** 없이는 새 계약서에 원본 텍스트를 제공하지 않는다.
- 이전 데이터 점검: 승인 문서 23개 중 20개가 `extracted_text`가 공란이었으며, 원본 ZIP의 이전 추출 자료에는 그 20개에 대한 텍스트가 남아 있었다. DB에 실제 입력되었는지 여부는 운영 복원 후 재검증해야 한다.

### 2026-11-13 · 운영 데이터 원문 복구 및 조항 위치 검증 (완료된 데이터 작업)
- Supabase `public.kekorea_contract_references`에서 기존 본문 누락 **20개**를 `contracts.zip`에서 검증된 원문 추출 결과로 직접 복구했다. SHA-256 20개 모두 원본 ZIP 및 기존 DB 해시가 일치했다. `private_text_extraction_v1`을 사용해 이전 OCR에서 미추출된 페이지와 수동 검토 필요 여부를 유지했다.
- 기존 승인 문서 3개까지 합쳐 공통 승인 **23/23개 `extracted_text` 보유**, **23/23개 `private_clause_hierarchy_v1` 비공개 인덱스 생성**. 총 원문 인덱스 **233개**, 모든 조항 ID 고유하고 조항 SHA256 검증 불일치 0개, 원본 해시 불일치 0개.
- 이 작업은 원문 저장 및 비공개 계층 인덱스 복원이다. **원문 233개가 모두 공통 AI 프롬프트로 승인된 것은 아님**. 원문 비교를 이용하려면 원문 앞뒤 맥락을 확인하고 익명화 참고 문구를 관리자 승인해야 한다.
- 기존 공통 승인 참고 메모 143개/임베딩 35개라는 별도 현황은 변경되지 않았다. 승인 참고 메모의 누락 벡터 생성과 실제 AI 비교 품질 및 Streamlit 운영 화면 배포 검증은 별도 확인 대상이다.
